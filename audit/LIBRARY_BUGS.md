## HIGH severity

- **[method_flags_width]** `vmhook.hpp:2252-2263 (get_flags returns std::uint16_t*) + write at 6065/6069` — get_flags() hard-codes std::uint16_t* and ignores vm_struct_entry_t::type_string (1612-1620). HotSpot Method::_flags is u1 on JDK 8-12, u2 on 13-20, u4 (+ sibling _flags2) on JDK 21+. On u1 the set_dont_inline RMW (*flags |= (1<<2) / &= ~(1<<2)) reads+writes the adjacent Method byte -> silent neighbour corruption. On u4 a u2 read sees only the low 16 bits, so flags that moved/grew into the upper half are unreadable (dont_inline bit-readback already downgraded to [INFO] on JDK21+ in dont_inline_dont_compile.cpp). Fix: dispatch load/store width on type_string.
- **[method_flags_width]** `vmhook.hpp:6065, 6069 (set_dont_inline RMW)` — The _flags read-modify-write (*flags |= (1<<2) / *flags &= ~(1<<2)) is a plain non-atomic operation, but HotSpot's own C2/JVMCI/JFR compile threads mutate the same word with Atomic::cmpxchg (set_dont_inline/set_hidden/set_caller_sensitive). vmhook can lose a concurrently-set bit either direction; most exposed on JDK21+ u4 where live JIT-state bits sit next to ours. Compounds the width bug (a too-wide RMW on a u1 field widens the lost-update window over a foreign field). Fix: atomic_ref fetch_or/fetch_and at correct width.
- **[interpreter_frame_walk]** `vmhook.hpp:7610-7688 (return_value::caller) vs 7737-7744 + 7767-7776 (stack_trace guards)` — caller() lacks BOTH hardening guards stack_trace() has: no monotonic/<=1MiB saved-rbp distance check, and it calls caller_method->get_name() (7652) / get_signature() (7661) with only is_valid_pointer(caller_method) (7644) and NO up-front ConstMethod/ConstantPool chain validation. Those getters deref the CP chain without per-step gates (the exact AV stack_trace was hardened against, observed on clang/JDK17). When the immediate caller is a compiled/native frame, caller() can land on a valid-looking bogus Method* and AV. Fix: route caller() through the same shared guarded walk (e.g. return stack_trace(1).front()).
- **[instanceklass_methods_walk]** `vmhook.hpp:2668,2700 (klass::get_methods_count / get_methods_ptr)` — Array<Method*> layout is hardcoded, not VMStruct-backed: _length read as raw int32 at array+0, data pointer returned as array+8. No static_assert, no offset query, no fallback. Correct on all current LP64 HotSpot but an unchecked ABI assumption — a 32-bit/non-_LP64/future layout makes +8 read one slot early and the whole enumeration becomes garbage Method*s (mostly skipped by per-slot is_valid_pointer, so symptom is wrong/short list, occasionally an AV).
- **[constantpool_access]** `vmhook.hpp:2975,2982 (find_field_in_stream) and 3094,3114 (find_field Array<u2> path)` — Field-stream constant-pool index reads dereference constant_pool_base[name_index]/[sig_index] with NO _length bound (cp->get_length()) and NO per-slot is_readable_pointer(&base[idx]) check — the exact two guards the method path applies at 2051-2059/2109-2117. is_valid_pointer on the loaded RESULT cannot help because the faulting read is base[idx] itself. A corrupt/over-decoded UNSIGNED5 or u2 index → access violation instead of recoverable nullopt.
- **[constantpool_access]** `vmhook.hpp:3114` — In the JDK8-17 Array<u2> path, constant_pool_base[sig_index] is loaded with no preceding non-zero/is_valid_pointer guard at all (unlike the name read at 3094). A field whose signature_index slot is 0 or out-of-range is still dereferenced; only the post-load is_valid_pointer(signature_symbol) at 3115 guards it. Most reachable variant of the asymmetry on JDK 8.
- **[method_entry_points_i2i_i2c]** `vmhook.hpp:8109-8154 (snapshot) vs 8829-8851 / 8922-8928 (teardown)` — original_from_interpreted / original_from_compiled / was_compiled are snapshotted into the hooked_method record at install but NEVER used by any restore path (shutdown_hooks and hook_handle::stop deliberately do not restore entries to avoid dangling-nmethod AVs). Dead state + load-bearing footgun: a future maintainer 'fixing' teardown to restore _code/_from_compiled_entry from these saved values reintroduces the post-uninject crash cascade.
- **[method_entry_points_i2i_i2c]** `vmhook.hpp:6122-6125 (validate_adapter_handler_entry)` — Hard-codes AdapterHandlerEntry::_i2c_entry at offset 0 instead of resolving it from VMStructs (the offset IS exported, like _c2i_entry). If a future JDK reorders AHE fields, validation reads the wrong slot and may spuriously PASS on a wrong offset, causing detect_adapter_offset_from_method to cache a bogus _adapter offset process-wide; every later deopt then writes a non-c2i pointer into _from_compiled_entry and the next compiled call jumps into garbage.
- **[adapter_recovery_c2i]** `vmhook.hpp:6122-6125` — validate_adapter_handler_entry reads _i2c_entry at a HARDCODED offset 0 via raw memcpy (comment 6104), unlike _c2i_entry which is resolved from VMStructs. AdapterHandlerEntry is exported in VMStructs with an _i2c_entry field, so this could be robust. If a future/patched HotSpot reorders the AHE, every real AHE fails validation, detect_adapter_offset_from_method returns 0, and the whole JDK9+ deopt feature silently degrades with no diagnostic.
- **[adapter_recovery_c2i]** `vmhook.hpp:6182-6191` — detect_adapter_offset_from_method skip set is std::array<size_t,8> and add_skip silently early-returns once full (6186). Six fields are added today (headroom), but it is a latent footgun: adding two more skips (or a JDK alias resolving to a distinct offset) makes the last add_skip a silent no-op, so the scan can then pick that real Method field's slot and return a wrong offset. No bounds diagnostic. Fix: size the array to the field count or assert on overflow.
- **[os_protect]** `vmhook.hpp:5621-5626 (midi2i_hook install)` — Trampoline installer calls os::protect(target, JMP_SIZE, execute_rw, &old) and then writes target[0]=JMP_OPCODE / *(int32*)(target+1)=delta WITHOUT checking protect()'s bool return. If the RW flip fails (kernel refuses the page, or W^X/sandbox denies PROT_WRITE|PROT_EXEC), the next store faults into read-only code and crashes the JVM. The sibling inline_hook installers (5654, 5739, 5791) correctly gate the write on the bool; this installer diverges. Fix: propagate the bool and set this->error=true on failure.
- **[os_query_region]** `vmhook.hpp:762-797 (macOS+iOS query_region) vs consumer vmhook.hpp:4875-4881` — macOS and iOS never set region_info.free (mac sets only committed=true; iOS hard-codes committed/readable). The trampoline hole-walk allocator only attempts placement when info.free is true, so the within-+/-2GiB gap search can never find a hole on Apple platforms and falls through to unconstrained allocate_rwx, defeating near-target placement (a correctness problem on arm64 rel-branch trampolines).
- **[os_query_region]** `vmhook.hpp:762-787 (macOS query_region) consumed at vmhook.hpp:1751-1752` — mach_vm_region's region_addr is in/out: for an address in an unmapped hole it returns the NEXT mapping, so info.base > address and the attributes describe a region the caller never queried. is_readable_pointer then reports the neighbouring region's readability for an actually-unmapped address -> false 'readable' verdict that can let a dereference fault. Windows/Linux report the containing region instead.
- **[os_safe_read]** `vmhook.hpp:919-924 (iOS arm of safe_read)` — iOS path does a raw std::memcpy and unconditionally returns true, violating the no-fault contract: a bad src faults the process (opposite of the API's purpose) and a successful read is indistinguishable from a failed one. Callers like safe_read_pointer (1856) trust the true return as 'dst is valid'. Latent (HotSpot/iOS combo doesn't exist) but the noexcept signature actively lies; should return false like the unknown-platform arm at 951.
- **[os_signal_handler]** `vmhook.hpp:5928-5938 (seh_invoke_detour non-MSVC branch)` — On non-MSVC toolchains (incl. mingw, which the __try form is gated out of via _MSC_VER && !__clang__ at 5918) the detour firewall is a plain catch(...), which does NOT catch a SIGSEGV/SIGBUS from a stale-OOP/null deref inside the detour. A real hardware fault is a signal, not a C++ exception, so it bypasses catch(...) and the JVM crashes — the exact outcome the 5899-5904 doc claims is prevented. The feature's central promise holds fully only on MSVC/Windows.
- **[os_signal_handler]** `vmhook.hpp:877-883 (detail_signal::install_once)` — sigaction(SIGSEGV/SIGBUS, &sa, nullptr) passes oldact=nullptr, discarding HotSpot's own SIGSEGV/SIGBUS handlers (implicit null-check, safepoint poll, stack-bang->StackOverflowError). After the first safe_read process_vm_readv fallback installs, a legitimate implicit-null-check fault on a non-probing thread hits vmhook's handler with active_state==nullptr, which resets to SIG_DFL (868-870) and re-raises -> process abort instead of HotSpot synthesizing an NPE. Breaks core JVM semantics process-wide on Linux; no chaining/restore of the prior handler.
- **[os_signal_handler]** `vmhook.hpp:5924 (seh_invoke_detour __except filter)` — __except(EXCEPTION_EXECUTE_HANDLER) handles EVERY SEH code unconditionally, including EXCEPTION_STACK_OVERFLOW (0xC00000FD). Swallowing a stack overflow without resetting the thread guard page leaves the next deep call to fault again with the guard gone (UB, frequently fatal). Also masks divide-by-zero/illegal-instruction/overflow traps as a benign 'detour skipped', hiding real user-detour bugs. Should filter to EXCEPTION_ACCESS_VIOLATION (and maybe IN_PAGE_ERROR) only.
- **[decode_u5_unsigned5]** `vmhook.hpp:2876 (decode_u5) vs. 2944-2972 (find_field_in_stream per-field loop)` — decode_u5 reads data[stream_pos++] with no internal length bound. The caller checks stream_pos < length only once per field (2944), but each field decodes 5 mandatory + up to 3 optional UNSIGNED5 values with no re-check between them, so a truncated/corrupt stream over-reads adjacent heap past arr_ptr+4+length. Fix: pass length/data_end into decode_u5 and re-check after each decode.
- **[array_element_helpers]** `vmhook.hpp:11579 and 11604` — Element byte-offset index * static_cast<int32>(sizeof(element_type)) is computed in 32-bit int and wraps before being added to the byte pointer. The bounds check only verifies index < length (length itself an untrusted raw int32 from guest memory), never that index*stride is in range. For an 8-byte stride any index >= 0x10000000 overflows (e.g. index 0x10000000 -> 0x80000000 == INT_MIN, sign-extended to a huge negative offset) -> wild read/write. Threat is a corrupted/attacker-controlled _length plus a large index. Fix: compute offset in size_t/ptrdiff_t.
- **[array_element_helpers]** `vmhook.hpp:11550 (read) consumed at 11758-11764, 15275+, 15663+` — array_length returns the raw int32 at base+12 with no sanity bound. A valid-looking oop with a garbage _length (stale object, mid-GC, unexpected layout) yields a huge positive count that flows straight into result.reserve(length) in read_array_value -- a multi-GB allocation / bad_alloc, and read_array_value is declared noexcept so the throw is std::terminate. Also makes bucket/collection walkers scan far past the real array. Negative length is partly contained (length<=0 early-outs, index>=length check) but huge positive is not.
- **[unified_call_syntax]** `tests/test_unified_call_syntax.cpp:42-48` — Existing test is compile-only: main() just prints OK, never starts a JVM, never registers a class, never checks that an instance call vs static call resolve to the right overload or return the right value. The entire runtime contract (instance site -> live OOP, static site -> class mirror, one spelling) is unverified.
- **[hook_common_detour_dispatch]** `vmhook.hpp:5984 + frame::get_method() 5005-5010` — common_detour validates `thread` (5979) but never `frame_pointer`, then calls frame_pointer->get_method() which raw-derefs *(Method**)(rbp-24). That read is inside the C++ try (5977) only, NOT the SEH firewall (seh_invoke_detour wraps only the user detour at 6012). A null/garbage/unmapped rbp — e.g. JDK21+ thread mid-transition at the injection instruction (per the 5958-5963 comment), or a stale frame after GC — raises an AV (SEH, not std::exception) that the C++ catch at 6027 cannot catch, tearing down the JVM. Fix: is_valid_pointer(frame_pointer) before 5984, or SEH-guard the get_method read.
- **[hook_common_detour_dispatch]** `vmhook.hpp:6002 (scan) vs 8158 (push_back); no reserve anywhere` — common_detour iterates g_hooked_methods lock-free (6002). Install push_back (8158) holds g_hooked_methods_mutex, but that mutex only serialises writers against each other — the reader holds no lock. The vector is never reserve'd, so a 2nd+ install can reallocate the backing buffer while a sibling method's detour is mid-iteration -> use-after-free on the std::function hook.detour cell (6012) / torn hook.method read. The install-site comment 8079-8081 explicitly (and incorrectly) claims the lock serialises 'against another thread's iteration in common_detour'. Triggered by verify_hooks/auto-repair re-install or any install-while-running. Fix: reserve to a cap, or snapshot under the mutex inside common_detour.
- **[midi2i_trampoline_alloc]** `vmhook.hpp:5397/5496 (ctor RESUME_JMP_OFFSET) vs 5777/5780 (rewrite_chain_resume private copy)` — Trampoline resume-JMP offset constants are duplicated per ABI in two places. If the assembly array is edited and only the ctor constants updated, verify_and_repair()->rewrite_chain_resume patches the resume rel32 at the wrong byte offset, corrupting the live trampoline. No test exercises rewrite_chain_resume at all. Needs single source of truth or static_assert.
- **[midi2i_trampoline_alloc]** `vmhook.hpp:5586-5587,5611,5613 (no self-validation of baked offsets)` — je-delta, resume rel32, and detour-pointer writes assume JE_OFFSET/RESUME_JMP_OFFSET/DETOUR_ADDRESS_OFFSET land on the right bytes of the assembly array, but nothing asserts assembly[JE_OFFSET]==0x0F/0x84 etc. A one-byte array edit shifts all landmarks; ctor still sets error=false and returns a hook that jumps to garbage. Needs static_asserts on the array bytes.
- **[seh_invoke_detour]** `CMakeLists.txt:128-135 (no /EHa) + vmhook.hpp:5918-5927` — MSVC __except arm relies on the default /EHsc EH model; /EHa is never set, so async (hardware) access-violation unwind through frames between the faulting decode (extract_frame_arg, 8137-8139) and the __except is not guaranteed. This is the single load-bearing flag for the library's crash-safety promise and it is absent.
- **[seh_invoke_detour]** `vmhook.hpp:5928-5937` — On MinGW/GCC/Clang the guard is a plain C++ catch(...), which catches C++ throws but NOT hardware SIGSEGV — the dominant real failure (stale-OOP deref in extract_frame_arg) sails through and aborts the process. No SIGSEGV-to-exception translation exists, so crash-safety is a no-op on 3 of 4 toolchains despite the doc comment (5902-5904) promising 0xC0000005 containment.
- **[seh_invoke_detour]** `vmhook.hpp:5918-5937 vs 8126` — C++ throws from a detour are handled asymmetrically: MSVC __except swallows the throw as raw SEH (0xE06D7363) with NO C++ catch semantics — intervening destructors and the return_value retval dtor (8126) are skipped; MinGW catch(...) runs them. Same detour => two unwind/leak behaviours by toolchain.
- **[find_class_context_loader]** `vmhook.hpp:6348 (find_class cache-hit guard) vs override_class_lookup doc 10737-10738 + .wip:344-349` — override_class_lookup(name, nullptr) does NOT create a working negative cache entry. find_class's cache-hit path requires `cached_klass && is_valid_pointer(cached_klass)` (6348); a cached null fails that guard and falls through to erase + fresh graph walk (6361-6367), so the class re-resolves non-null on the very next find_class. The doc claims it 'seeds a negative entry' and the quarantined module asserts find_class(name)==null after a null override — both are wrong. The negative-cache feature is effectively a no-op.
- **[find_class_context_loader]** `vmhook.hpp:9276-9281 (jni_oop_handle) used by find_class_via_oop:10656 and inherit_*:9831` — find_class_via_oop passes a RAW oop through JNI as a fake handle (jni_oop_handle stashes the oop and returns &storage; HotSpot dereferences *handle expecting a stable oop). The call is not in a no-GC scope and the oop is not rooted in a real handle, so a GC moving the anchor between obtaining the oop and the JNI read => GetObjectClass on a stale/forwarded address. The public API gives callers no safety contract; the .wip only avoids it by passing a detour-local self->get_instance().
- **[dllmain_bootstrap]** `vmhook/src/example.cpp:3339-3344 (launch_worker_once)` — Process-lifetime std::once_flag means a DLL FreeLibrary+LoadLibrary cycle never re-spawns the worker. Directly contradicts the now-reversible shutdown_hooks() (vmhook.hpp:8858-8868) which was made resettable for the mod-loader teardown+re-init pattern; the bootstrap defeats it. Fix: resettable atomic flag cleared by explicit teardown, not call_once.
- **[dllmain_bootstrap]** `vmhook/src/example.cpp:3204 (run_test_suite, sleep_for 2s)` — The fixed 2s sleep is the ONLY JVM-readiness gate. No find_class/get_instance poll, no JavaVM-attached check. On a slow/loaded/debugged JVM, example_class::get_instance() (3222) returns null, if(instance) (3224) fails, and the ENTIRE suite is skipped after one Example.instance=false (3322). register_class already reports not-loaded via its false return (vmhook.hpp:6921-6925) but the bootstrap ignores it. Fix: bounded poll on find_class/get_instance.

## MEDIUM severity

- [vmstructs_offset_resolution] `vmhook.hpp:1711-1730 (resolver) + struct 1617-1619` — iterate_struct_entries returns the entry but never inspects is_static. offset vs address is a real HotSpot union: for a static field ->offset is garbage, for an instance field ->address is garbage. Correctness depends on each of ~130 call sites hand-picking the right member; entry->is_static is read NOWHERE (the is_static reads at 11076/11135 are the unrelated field_entry_t). Verified all current ->address/->offset readers are correct today, but a JDK change or a new caller copying the wrong idiom silently reads garbage with no diagnostic.
- [compressed_oops_decode] `vmhook.hpp:4418-4421 (encode_oop_pointer)` — Below-base guard `if (decoded_address < narrow_oop_base) return 0;` silently maps any non-null sub-base pointer to the null compressed oop (0). With a non-zero heap base (~4-32GB heaps) a foreign/stale pointer is encoded as 'store null', nulling a live Java reference with no diagnostic and no error sentinel distinct from legitimate null / no-JVM.
- [compressed_oops_decode] `vmhook.hpp:4423 (encode_oop_pointer)` — Final `static_cast<uint32_t>((addr-base)>>shift)` has no upper-bound check and no shift-residue/alignment check. An address beyond the 4GB<<shift representable range is silently truncated to a valid-looking-but-wrong narrow oop; a misaligned `decoded` loses its low `shift` bits. So encode(decode(x)) / decode(encode(p)) are only guaranteed to round-trip through null, not for arbitrary or unaligned values.
- [compressed_klass_decode] `vmhook.hpp:4494 (decode_klass_pointer)` — Decode returns base+(compressed<<shift) for ANY non-zero input with no alignment or class-space-range check; only the caller's is_valid_pointer gate (14606/13557/10405) catches anything, and a wrong-but-canonical pointer passes it. A torn/garbage narrow-klass word yields a plausible bogus Klass* that flows into get_name/field/method resolution. The primitive itself never enforces (result&0x7)==0 nor result in [base,base+2^(32+shift)).
- [compressed_klass_decode] `vmhook.hpp:14603-14604 (klass_from_oop) and 13554-13555 (klass_from_object_header)` — Narrow klass is read at a hard-coded oop+8. Correct for the traditional header but WRONG under -XX:+UseCompactObjectHeaders (Lilliput/JEP 450, preview in JDK 24/25) where the klass is packed into the mark word and +8 is the first instance field. No compact-header detection anywhere; would decode an instance-field bit pattern into a wrong klass that still passes is_valid_pointer.
- [compressed_klass_decode] `vmhook.hpp:14603-14604 / 13554-13555 (4-byte read) feeding 4433` — No handling for -XX:-UseCompressedClassPointers (or 64-bit JVM with class ptrs off): the +8 slot then holds a full 64-bit Klass*, but the readers unconditionally read 4 bytes and route through the narrow decoder. Result is either nullptr (VMStruct absent) or base+(truncated_low32<<shift) garbage. Feature silently assumes compressed class pointers are ON; no 64-bit fallback.
- [klass_introspection] `vmhook.hpp:6983-6984 (collect_klass_methods) -> 2661/2689 (get_methods_count/get_methods_ptr)` — No klass-kind check before reading the InstanceKlass::_methods VMStruct offset. find_class can resolve an ArrayKlass (e.g. "[I", "[Ljava/lang/String;"), which is not an InstanceKlass; the cached _methods offset then applies to a differently-shaped object. Saved today only by downstream is_valid_pointer(array)+count<=0 bailouts (usually returns empty), but it reads a field that does not exist on that klass kind. Gate on Klass._layout_helper / oop_is_instance before touching _methods.
- [klass_introspection] `vmhook.hpp:2668 (get_methods_count) -> 6989/6990 (collect_klass_methods reserve+loop)` — Array<Method*>::_length is trusted as an unbounded reserve/loop bound. Negatives are filtered (count<=0) but a corrupt large-positive length drives reserve(static_cast<size_t>(count)) (huge alloc / length_error, swallowed by outer catch -> silent empty) and indexes methods_array[0..count) past the real array end; only the per-element is_valid_pointer prevents the deref. Clamp count to a sane ceiling like the 0x1000/0x4000 caps used elsewhere.
- [const_method_bounds] `vmhook.hpp:3094 + 3114 (klass::find_field) and 2975-2977 + 2982-2984 (klass::find_field_in_stream)` — FIX B's bounds guard (ConstantPool::get_length() bound + is_readable_pointer(&base[index])) was applied ONLY to const_method::get_name/get_signature. The twin field-symbol readers index the SAME ConstantPool::get_base() array with a u2 name_index/sig_index from class metadata and dereference base[index] BEFORE is_valid_pointer validation — the identical out-of-bounds/AV hazard FIX B closed for methods is still open for fields. Belongs in a shared constant_pool::symbol_at(index) helper. (find_field also reads JDK8 Array<u2> field-record slots at 3088-3103 without bounding field_slot_index*6+5 against the array _length read at 3061.)
- [method_flags_width] `vmhook.hpp:6054-6071 (set_dont_inline) + 2252-2263 (get_flags)` — set_dont_inline calls method_pointer->get_flags() with NO null/is_valid_pointer guard (6057), unlike every other method:: accessor; get_flags() itself also does no validation and indexes this+offset blindly. Verify/repair + shutdown call sites can pass a null or freed/aliased Method* (post class-unload / RedefineClasses) -> AV inside set_dont_inline on Windows (RO/freed page) or silent foreign-write on Linux. Fix: add if(!method_pointer || !is_valid_pointer(method_pointer)) return;.
- [method_flags_width] `vmhook.hpp:2257-2260 (get_flags absent-entry path)` — When the Method::_flags VMStruct is absent, get_flags() returns nullptr with NO VMHOOK_LOG and no try/catch, so set_dont_inline silently no-ops. Asymmetric with get_access_flags/get_const_method/get_i2i_entry which all log on the same failure. User gets a 'true' install (install path only checks _access_flags) but silently loses inline-protection; the JIT inlines past the i2i patch later with no breadcrumb. Fix: match the surrounding try/catch + VMHOOK_LOG(error_tag) pattern.
- [interpreter_frame_walk] `vmhook.hpp:4647 (decl) + 4739 (write) locals_offset` — locals_offset is a single process-global int8 written last-writer-wins by find_hook_location for every i2i stub scanned. Two stubs with different mov r14,[rbp+disp] displacements (mixed/future JVM stub layouts) make the second scan's offset apply to get_locals() for both methods, silently mis-reading the first method's locals. If the 4C 8B 75 ?? C3 pattern fails to match (4734-4742 falls through, no error), the stale/-56 default is used. No per-stub storage, no consistency check.
- [interpreter_frame_walk] `vmhook.hpp:5050-5066 (frame::get_locals JDK-era heuristic)` — The slot value is a direct pointer iff is_valid_pointer (5053), else an index iff < 0x1000 (5061), else nullptr (5066). A legal JDK-21+ frame whose recovered index is >= 0x1000 (max_locals is a u2 up to 0xFFFF) silently yields nullptr, making every typed-arg decode return defaults with no diagnostic. The 0x1000 cutoff is a magic constant unrelated to the real 0xFFFF max_locals bound used elsewhere in the feature.
- [interpreter_frame_walk] `vmhook.hpp:7479 (extract_frame_arg decode_oop), mirrored 5291 (get_argument) and 5182 (get_arguments)` — The narrow-OOP heuristic bits <= 0xFFFFFFFF is ambiguous: with -XX:-UseCompressedOops (large heaps) a genuine uncompressed heap pointer below 4 GiB is wrongly run through decode_oop_pointer, corrupting the decoded self/String/wrapper.
