# vmhook authoritative audit findings

Read-only audit of the vmhook library. Drives the refactor/fix pass. Act on high-severity bugs and the rework_d retirement first, then dead-code, then structure/improvements/docs.

This document is consolidated from two waves:
- **Wave 2 (2026-06-20, current)** — 16 subsystem re-audits (4 clusters: `os_protect`, `vmstructs_offset_resolution`, `find_class_fallback`, `jvm-test-harness-and-driver`), verified against **current source** (header is now ~21434 lines; Wave-1 line numbers were ~3000 lines stale). These findings are authoritative where they overlap Wave 1.
- **Wave 1 (2026-06-06)** — original 14-cluster per-file sweep (181 findings). Retained below as the broad catalog; its `vmhook.hpp` line numbers are systematically stale (drift grows with file position) and several items it lists are already fixed. Reconcile against current source before acting.

Where a Wave-2 finding supersedes or confirms a Wave-1 item, the Wave-1 entry is annotated `[SUPERSEDED by Wave-2 …]`.

## Executive summary

**Wave-2 (current, source-verified): 30 findings.**

By severity: high=5 (1 bug + 4 rework_d), medium=7, low=18.
By category: bug=6, rework_d=6, structure=5, improvement=7, doc_gap=5, dead_code=1.

**Highest-leverage items (do these first):**

1. **HIGH bug — JDK8/CDS bucket-chain truncation** (`vmhook.hpp:4342-4365`, `4392-4414`). `untag_pointer` clears the high GC bits but leaves bit 0, so every CDS-archived BasicHashtableEntry (default `classes.jsa` covers most `java/lang/*`) is rejected as an odd pointer and the dictionary walk truncates. `for_each_loaded_class` silently omits those classes permanently (no JNI fallback). Fix: clear bit 0 right after each bucket-head / `_next` read, before the validity gate.
2. **Rework D — retire the legacy test lane.** The driver runs two parallel lanes in one process; the legacy lane (36 inline `test_*()` in `example.cpp`, the `runProbe` block in `Main.java:48-275`, the 10 top-level Java fixtures, and the example/wrapper classes) is fully duplicated and superseded by 83 `tests/jvm/modules/*.cpp`. Retire it down to a thin modular-only driver. Clear 3 blockers first (warmup sufficiency, `for_each_loaded_class` anchor, `verifySetterEffects` port).
3. **MEDIUM bug — array names unresolvable through the JNI fallback** (`vmhook.hpp:12064-12139`). `load_with_loader` calls `ClassLoader.loadClass`, which cannot resolve `[I` / `[Ljava/lang/String;`; `find_class("[…")` returns null even though `jni_find_class` (real `FindClass`) would succeed. Add a `starts_with('[')` fast-path routing through `jni_find_class`.
4. **MEDIUM bug — DR hardware-breakpoint alignment** (`vmhook.hpp:20888`/`20851-20855`/`20829`). `watch_static_field` arms an x86_64 data breakpoint with `LEN` from `sizeof(field_type)` but never checks the address is naturally aligned; an unaligned DR address misfires/misses per the Intel SDM. Assert alignment (or fall back to 1-byte LEN).
5. **MEDIUM bug — `iterate_struct_entries` drops `is_static`** (`vmhook.hpp:1990-2009`). The resolver never surfaces `is_static`, so the offset-vs-static-address read discipline is hand-picked at ~130 call sites with no validation — a future JDK flipping a field's static-ness silently reads garbage. Expose typed `resolve_offset` / `resolve_static_address` accessors that assert.
6. **MEDIUM — resolver success path is untestable** (`vmhook.hpp:1990-2009`). The most depended-upon primitive has zero pure-logic coverage because `iterate_struct_entries` reads the global head internally with no array seam. Factor a `find_struct_entry(head, type, field)` free function to add a test seam.
7. **MEDIUM bug — `for_each_loaded_class` couples to legacy launcher identity** (`for_each_loaded_class.cpp:653,673`). It HARD-asserts `vmhook/Main` is enumerated and INFO-observes `vmhook/Example`; re-anchor to its own `ForEachLoadedClass`/`$Inner` fixture before retiring the legacy lane.
8. **MEDIUM doc/contract — `protect()` `old_prot` is platform-asymmetric** (`vmhook.hpp:644-647`, `688-691`). Windows writes the real prior flags; POSIX always writes 0. A naive save/restore caller bricks the page on Linux/macOS. Document at the signature (Wave-1 also flagged this).

The single HIGH item (CDS truncation) plus the Rework-D retirement are the dominant work. Everything else is medium/low and largely defensive/structural.

### bug

| Location | Subsystem | Severity | Finding | Fix direction |
|---|---|---|---|---|
| `vmhook.hpp:4342-4365`, `4392-4414` | find_class_fallback | high | CDS bucket-chain truncation (see High priority). | Clear bit 0 after each bucket-head/`_next` read. |
| `vmhook.hpp:12064-12139` (load_with_loader) | find_class_fallback | medium | **Array-class names unresolvable via the JNI fallback.** `load_with_loader` calls `ClassLoader.loadClass(String)`, which cannot resolve array descriptors (`[I`, `[Ljava/lang/String;`); all three loader paths throw `ClassNotFoundException` and the function returns null even though `jni_find_class` (real `FindClass`, accepts array names) would succeed. Downstream callers resolving element types of objArrayKlasses / reflection wrappers see spurious misses. | At the top of `jni_find_class_with_context_loader`, detect `class_name.starts_with('[')` and route through `jni_find_class` + `jni_klass_from_class_mirror` (clearing the pending exception on miss), skipping the `loadClass` chain. (The CDS fix lets most array klasses resolve via the graph walk first — hence MEDIUM not HIGH.) |
| `vmhook.hpp:20888` + `20851-20855` + `20829` | os_protect / DR7 | medium | **DR hardware-breakpoint not alignment-checked.** `watch_static_field` arms an x86_64 data breakpoint on `proxy->raw_address()` with `LEN` derived from `sizeof(field_type)` but never verifies natural alignment. Per the Intel SDM the DRn linear address must be aligned to the LEN encoding; an unaligned address yields an unpredictable/misfiring `#DB` (can miss writes or trap adjacent bytes; some µarches silently mask the low LEN bits). A Java static landing unaligned for its type produces a watch firing on the wrong bytes. | Before `build_dr7`, assert `(uintptr_t(address) & (len_in_bytes-1)) == 0`; on misalignment reject with a logged error (empty `watch_handle`) or fall back to 1-byte LEN at the exact address. |
| `vmhook.hpp:1990-2009` (struct `1896-1898`) | vmstructs_offset_resolution | medium | **`iterate_struct_entries` drops `is_static`.** Returns the raw `vm_struct_entry_t*` but never inspects `entry->is_static`, so it never tells the caller whether to read `->offset` (instance) or `->address` (static). vmhook lays these out as two separate members (not a union); correctness depends on all ~130 call sites hand-picking the right member. Verified correct today, but a future JDK flipping a field's static-ness, or a new caller copying the wrong idiom, silently reads garbage with no diagnostic. | Expose typed accessors: `resolve_offset(type,field)` asserting `!is_static`, `resolve_static_address(type,field)` asserting `is_static` (return `nullopt`/`nullptr` on mismatch); or at minimum validate `is_static` against the member the caller intends to read. |
| `vmhook.hpp:1921-1936` (get_vm_types), `1944-1959` (get_vm_structs) | vmstructs_offset_resolution | low | **One-shot nullptr cache hazard.** Both getters cache a function-local static head from `get_proc_address(get_jvm_module(), "gHotSpotVMStructs")`; `get_jvm_module()` also caches once. If any resolver runs before the JVM library is mapped (early injection, lazy `LoadLibrary`, JVM loaded later), the nullptr is cached permanently and every later lookup returns nullptr even after `jvm.dll`/`libjvm.so` appears. Plausible for an injection/RE library. | Memoise only a NON-null head; on null, re-probe `get_jvm_module()` (which must itself re-probe after a prior null) each call until a JVM appears, at bounded retry cost. NOTE `tests/test_iterate_entries_safety.cpp` (~51-81) deliberately asserts pointer-identity permanence across 1000 no-JVM calls — a fix must distinguish "no JVM yet" from "no JVM ever". |
