### Highest-leverage items (do these first)

1. **HIGH — register_class factory-map asymmetry → cross-type UB** (`vmhook.hpp:8767` insert_or_assign vs `8775` emplace; manifests `9417-9429`). The type map overwrites, the factory map does NOT; two C++ wrappers naming the same Java class alias one factory, and `extract_frame_arg` `static_cast<element_t*>`-downcasts across unrelated types. Verified in current source. Fix: key the factory map by `std::type_index` (or `insert_or_assign`).
2. **HIGH — `hook_handle::stop()` erase races the lock-free dispatch reader** (`vmhook.hpp:11178` erase vs `7187` unlocked range-for). `vector::erase` shifts/moves `std::function` detour cells while `common_detour` may be mid-scan on a sibling hook → torn `method` read / half-moved `std::function` invocation / UAF. Verified. Fix: tombstone-in-place (set method=nullptr, compact only under the shutdown freeze) or snapshot under the lock.
3. **HIGH — `call_jni` per-proxy caches never invalidated across overloads** (`vmhook.hpp:16258` resolve vs `16282/16324` cache-on-first). A reused name-only proxy resolving a different overload dispatches the FIRST overload's `jmethodID` + return-decode char → wrong method / wrong-typed return on the JDK21+ JNI path. Fix: key the cache on the resolved `Method*` (recompute on change), or recompute `ret_char` every call as the call_stub path already does.
4. **HIGH — `for_each_thread` raw struct derefs on the no-SEH legs** (`vmhook.hpp:8486-8506` Path 2; `4804/4814` `get_os_thread_id`; `4937` `find_any_java_thread`). Raw `is_valid_pointer`-only derefs of VMStruct-offset-derived addresses — the exact #28 cold-fault crash class `for_each_instance` was hardened against; a misresolved offset that passes the heuristic but hits an unmapped page tears down the JVM on MinGW/clang-on-windows. Fix: route every read through `os::safe_read`/`safe_read_pointer`, bail on first failure.
5. **HIGH — uncompressed-class-pointer klass-read path missing** (`vmhook.hpp:18826` klass_from_oop, `17306` klass_from_object_header, `8690` scanner, `13306` diagnostic). All four object-header klass readers hardcode `+8` and read a 32-bit narrow klass + `decode_klass_pointer`, with NO `-XX:-UseCompressedClassPointers` fallback — even though the writer `make_java_object` (`14123-14140`) resolves both. With compressed class pointers off, every runtime klass reads back as garbage/null. Fix: factor one resolved-offset header reader handling both layouts.
6. **HIGH — `set_prim_array` strides by C++ type, not array element width** (`vmhook.hpp:20502-20531`). `set_prim_array<int64_t>` on `int[]` strides 8B over a 4B array; past length/2 it writes past the data and corrupts heap. The read path (`14806-14819`) already guards this. Fix: add the read-path width guard via `jvm_primitive_byte_width(sig.substr(1))`.
7. **HIGH — static primitive `set()` writes a stale cached field pointer after relocating GC** (`vmhook.hpp:15552-15614`). `get()`/`get_compressed_oop()` re-resolve the live static mirror; the primitive write memcpys the cached `field_pointer` with no `mirror_klass` re-resolve, no `is_valid_pointer`, no `safe_write` → writes a stale/wild address after GC. Companion: the `unique_ptr` reference write (`15532-15551`) has the same gap. Fix: re-resolve via `mirror_klass`, gate `is_valid_pointer`, route through `store_object_oop`/`safe_write`.
8. **HIGH — JDK8/CDS dictionary bucket-chain truncation** (`vmhook.hpp:4364`, `4413`). `untag_pointer` masks with `0x00007FFFFFFFFFFF` which preserves bit 0 — the CDS shared-entry `_next` marker — so the chain advance produces an odd address that the next `safe_read_pointer`/`is_valid_pointer` rejects; the walk stops at the first shared entry. `find_class`/`for_each_loaded_class` silently omit CDS-archived classes. Fix: `& ~uintptr_t{1}` on the chain pointer before the canonical untag, in both `find_klass` (4364) and `for_each_klass` (4413).
9. **HIGH — injector `GetExitCodeThread` success detection truncates the 64-bit HMODULE** (`injector/src/main.cpp:177-189`). `LoadLibraryW`'s 64-bit return is truncated to the 32-bit thread exit code; a module whose base low-32-bits are zero is mis-reported as failure — the canonical CreateRemoteThread+LoadLibrary x64 bug and the source of past intermittent "Injection failed". Fix: verify presence via remote module enumeration (Toolhelp32 SNAPMODULE), treat exit code as a coarse liveness hint only.

Plus the **Wave-2 rework_d legacy-test-lane retirement** (retire 36 inline `test_*()` + the `Main.java` probe block + 10 top-level Java fixtures; superseded by 83 `tests/jvm/modules/*.cpp`) — the dominant structural cleanup, mapped in the appendix.

The nine HIGH bugs plus the legacy-lane retirement are the bulk of the work. Everything else is medium/low — mostly defensive hardening, doc contracts, and consistency.

- **fields** — static `raw_address()` (`15645-15648`) returns the cached `field_pointer` and cannot re-resolve after a relocating GC; document the GC-staleness (a `watch_static_field` breakpoint would watch a dead address).
- **find_class_fallback** — `dictionary::find_klass`'s inner bucket-chain loop (`4346-4365`) has no visit cap while `for_each_klass` (`4397`) caps at `1048576`; add the same bounded counter for hang safety (especially once the CDS bit-0 fix walks further into chains).
